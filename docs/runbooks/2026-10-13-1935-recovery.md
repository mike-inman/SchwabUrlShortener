# Recovery runbook — 2026-10-13 19:35 CDT

Scope: the single `prod` environment in `rg-schwab-url-shortener`, subscription `baaf4acd-ff40-43d1-a7ba-6089a2c4f41e`. This is a procedure, not a tested recovery. Obtain incident approval before changing resources or application data. Preserve the original server and all secrets until the restored service is verified.

1. Confirm the active Azure account and subscription, incident time, affected resource IDs, latest successful backups, and current image digests. Record the incident and stop writers if data integrity is uncertain. Do not remove the resource-group `CanNotDelete` lock as a routine recovery step.
2. Restore PostgreSQL Flexible Server to a **new** server name at the chosen point in time, with private VNet access in the delegated subnet and the linked private DNS zone. Keep the original server. Confirm PostgreSQL version, database name, private-only access, TLS settings, and that the restored endpoint resolves from the Container Apps environment. A restore is not an in-place rewind.
3. Take a controlled backup/export if possible before switching. Create a new version of `pg-app-connection` and `pg-migrate-connection` in Key Vault for the restored host, using hidden input and preserving the previous versions. Keep `Maximum Pool Size=2` in the app connection and direct port 5432 for migrations. Reconcile the secure azd password input so a later Bicep provision does not restore stale secret values.
4. Restart or revise the affected API, Analytics, and migration job references to pick up the new secret versions. Run the migration job only once after confirming schema compatibility with the deployed image. Do not run migrations against the original server during diagnosis.
5. Verify API and Web readiness, one guest redirect, one authorized managed-link request, outbox-to-Analytics flow, and aggregate counts. Confirm no data is missing before moving traffic. Record restore time, recovery point, and observed data loss.
6. Redis is a cache. Restart the Redis app and verify its Azure Files AOF volume; if the AOF is unusable, preserve it for diagnosis, replace the cache volume only with approval, and let the application refill from PostgreSQL. Never treat Redis as the source of link ownership or click history.
7. If the environment itself is lost, recreate only the approved resource group through the committed Bicep and digest images, restore PostgreSQL to a new private server, reapply least-privilege role assignments, then run the same smoke checks. Record which steps were exercised and the recovery time. The trial spending limit and single-region design can still interrupt service.

Production upgrade: zone-redundant PostgreSQL high availability and a second region reduce recovery time but add recurring cost. Test this runbook on a disposable environment before relying on it operationally.
